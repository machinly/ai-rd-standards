# 提案：建立操作模型抽象层与多 Agent 编排规范

## 意图

当前规范已经有 W0-W9 工作流主线和角色泳道，但距离"完全无人值守、7x24 自主运转的 AI 虚拟公司"这一目标存在三个结构性缺口：

1. **缺少抽象方法论层**。现有文档直接从工作流细节开始，方法论原则散落在各专项里，且与 Go/Kratos/Vite 等技术栈细节混杂。没有一个与技术栈无关、可长期稳定的"为什么这样运转"层。
2. **多 Agent 协作描述过薄**。`docs/03-role-index.md` 只定义了总控 Agent 和角色 Agent 的输出契约，缺少任务契约、通信规则、并发纪律、失败升级、状态恢复和无人值守门禁——这些恰恰是多 Agent 系统的生死线。
3. **参考依据过窄**。现有来源集中在人月神话、小型项目管理、Google SRE 和 OpenAI 文档；2025-2026 年业界（Anthropic、Cognition、LangChain、Factory、HumanLayer 等）和学术界（MAST、Magentic-One、MAKER、TheAgentCompany、METR 等）关于 multi-agent 编排与长时自主系统的成果尚未吸收。
4. **中心文档尚未落到每个 W 与专项**。初始版本只新增 L0/L1 中心文档和导航，容易让下一个 Codex 知道“有两份新文档”，却不知道 W0-W9 各阶段和触发专项应该如何具体执行这些原则。

这个变更新增两层文档并挂接导航：

- `docs/04-operating-model.md`：L0 操作模型抽象层。回答"这家虚拟公司凭什么能自主运转"，只写与技术栈无关的系统模型、第一性原则和自主性梯度。
- `docs/05-agent-orchestration.md`：多 Agent 编排规范。回答"总控和工人 Agent 具体怎么协作"，定义任务契约、通信管道、执行循环、并发纪律、失败升级和无人值守门禁。

本轮在原 change 名称下扩展范围：不重命名 change，但把落地目标从“新增中心文档和导航”扩展为“W0-W9 主入口和 30 个触发专项逐个承接操作模型、Agent 编排协议和小型项目管理原则”。

## 范围

- 新增 `docs/04-operating-model.md`（抽象方法论层）。
- 新增 `docs/05-agent-orchestration.md`（编排协议规范）。
- 更新 `README.md`、`docs/00-start-here.md`、`docs/02-standard-index.md`、`docs/03-role-index.md`，把两层新文档挂进导航；角色泳道声明为编排规范中 worker 的专业化配置。
- 更新 `knowledge/context-packs/rd-standards.md` 的 System Shape 与 AI Behavior。
- 在 `docs/sources/2026-06-23-source-map.md` 追加 2026-07-03 的编排与自主系统依据章节。
- 逐个更新 `docs/W0-intake/00-main.md` 到 `docs/W9-maintain/00-main.md`，只加入该阶段如何承接 L0 操作模型、L1 Agent 编排和小型项目管理的简短执行条款。
- 逐个更新 `docs/W*/` 下 30 个非 `00-main.md` 触发专项，只加入该专项如何承接 L0/L1、小项目原则、task packet/write scope/DoD 或 T2/T3 人审口径的简短执行条款。
- 更新 `docs/sources/2026-07-08-small-project-management-operating-guide.md` 的纳入状态，并在 source map 中登记小型项目管理资料到 W0-W9 的吸收关系。

## 不做什么

- 不重排、不重命名 W0-W9；工作流主线和角色泳道原样保留。
- 不把 L0/L1 长原则复制进 W0-W9 或每个专项；每个 W 和专项只写本阶段/本专项如何执行，并保持职责边界清晰。
- 不在本变更中实现任何运行时代码（队列、调度器、status 工具）；先立规范，实现另开 change。
- 不删除现有触发专项；W3 专项的方法论/技术栈拆分留给后续维护 change。
- 不承诺"立即可无人值守"；规范按自主性等级渐进放权，当前默认等级仍保留人审门禁。

## 需要人的判断

- 是否接受"操作模型 + 编排规范"作为 W0-W9 之上的两层新入口。
- 是否接受自主性等级 A0-A4 的划分和默认放权条件。
- 是否接受"生产发布默认挂起到升级队列，自动化只到发布候选和预检证据"的无人值守安全立场。
- 后续是否投入实现 change（任务队列、状态账本、验证门禁工具化）。
- 是否将小型项目计划模板进一步固化为 `planning/` 下的独立工件；本轮先把原则纳入 W0-W9 主入口和触发专项，不新增模板目录。

## 落地 Review

### Review A：一人可执行性

- 这次变更可以由一个人在一个专注工作块内执行：新增两份入口文档、一个 OpenSpec change、导航挂接和来源补充，不要求立即实现调度器。
- 复杂度有分层边界：L0 只放原则，L1 放编排协议，W0-W9 和触发专项只加短执行钩子，避免把所有细节塞进单个入口。
- 中断恢复路径明确：变更意图、设计、任务清单、spec 和验证结果都在 `openspec/changes/add-operating-model-and-agent-orchestration/`；后续 Agent 可以从这些工件继续。
- 本轮扩展后，W0-W9 每个主入口都能告诉下一个 Agent：本阶段如何接住操作模型、编排协议和小型项目管理，而不是只把读者导向两份中心文档。
- 第二轮扩展后，30 个触发专项也能告诉下一个 Agent：本专项的工件如何成为任务契约、验收证据、写域边界、升级队列或 T2/T3 人审点。
- 下一步仍是小而明确的实现 change：先为一个真实小项目试运行 M1/M2，沉淀 `status.md` 模板和最小验证门禁脚本。

### Review B：产品 / 工程 / 运维风险

- 主要风险是过早放权。当前规范把无人值守默认限制在 T0/T1 和发布候选；生产发布、生产迁移、生产配置变更默认挂起，T3 动作永远人审。
- 验收标准已落到机器可验证工件：`python tools\verify_workflow_index.py .` 与 `openspec validate --all` 必须通过；多 Agent 任务进入无人通道前必须有机器可判定 DoD。
- 运维风险有明确防线：有界队列、三级预算、熔断、停滞计数、失败分类账和升级队列，避免死循环、成本失控和越权动作。
- 数据、安全、隐私与回滚边界仍需后续工具化；在工具化前，最小安全下一步是只在 T0/T1 文档或代码批次上试运行，不触碰生产副作用。
