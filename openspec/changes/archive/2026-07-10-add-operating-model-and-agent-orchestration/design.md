# 设计：操作模型抽象层与多 Agent 编排规范

## 分层决策

采用四层结构，自上而下稳定度递减：

```text
L0 操作模型（docs/04-operating-model.md）
    与技术栈无关的系统模型、第一性原则、自主性等级。换模型、换工具、换语言都不需要改。
L1 编排协议（docs/05-agent-orchestration.md）+ W0-W9 工作流 + 角色泳道
    编排协议回答"agents 怎么协作"；W0-W9 回答"工作处于生命周期哪一步"；角色泳道回答"谁参与"。
L2 各 W 主入口（docs/Wx-*/00-main.md）
    每步的核心问题、最小产出、人审点。
L3 触发专项（docs/Wx-*/0N-*.md）
    技术栈细节，按触发条件读取。
```

理由：用户反馈"全是细节、缺抽象层"。把最稳定的方法论提到 L0，参数和协议放 L1，技术栈细节留在 L3，各层变更频率不同，互不拖累。

## 关键设计决策

### 1. 新文档放 docs/ 根、编号 04/05

与 00-03 导航文件同级。不放进 W 目录（它们跨全部 W），不新建目录（两个文件不值得一层目录，克制文件数量）。`tools/verify_workflow_index.py` 只校验 W 目录内编号连续性，此布局不冲突。

### 2. 写路径单线程、读路径并行，作为并发纪律的核心公理

Cognition 与 Anthropic 的实战结论一致：并行探索收益大，并行写入产生冲突的隐式决策。编排规范规定：同一文件域同一时刻只有一个 writer；研究、审查、检索类任务允许 fan-out。这与 Go 的"通过通信共享内存"心智模型吻合。

### 3. 任务契约四要素 + 机器可判定 DoD 是无人值守准入线

任何任务没有 objective / output format / 来源与工具指引 / 边界 四要素不得派发；没有机器可判定完成判据（测试、schema、策略引擎）不得进入无人值守通道。依据：Anthropic multi-agent research 的委派失败案例、MAST 验证缺陷占 23.5%、Devin"可验证结果"任务画像。

### 4. 双账本 + 停滞计数器作为防循环卡死机制

采用 Magentic-One 的 task ledger / progress ledger 双循环与 stall counter（≤2 触发重规划）。MAST 数据显示"步骤重复 + 未察觉终止"合计约 28%，是无人值守系统第一死因，必须有结构性防御而不是靠模型自觉。

### 5. 状态全部外置、append-only、可重放

进度台账、任务账本、批次日志全部落文件并纳入 git；执行者无状态（可 kill-restart-resume）。依据：Anthropic managed agents 的 session log、Springdrift 23 天实证、12-Factor Agents #5/#6/#12。

### 6. 副作用分级默认 deny、问责保留

生产动作（发布、迁移、配置）和不可逆/对外动作（付款、承诺、对外通信、删除数据、凭据操作）过确定性策略门；无人值守时 T2 生产动作默认挂起到升级队列，只允许自动准备发布候选与预检证据，T3 动作永远人审。Project Vend 两期与 Magentic-One 事故记录表明 helpfulness 偏置会被系统性利用，这条不做模型判断，做确定性规则。

### 7. 自主性是等级不是开关

A0（全程人审）到 A4（目标级委托）五级，放权条件绑定验证覆盖率与历史通过率（pass^k），不绑定主观信任。与 Anthropic autonomy 研究的"渐进赢得信任"曲线一致。

### 8. W0-W9 只接执行钩子，不复制 L0/L1

本轮把中心文档落到每个 W 主入口，但采用“阶段执行条款”而不是复制原则：W0 只管入口取舍，W1 只管证据和成功标准，W2 只管 OpenSpec、风险和计划粒度，W3 只管 AI 行为验收，W4/W5 只管小批量实现和证据闭环，W6/W7 只管发布与运行责任边界，W8/W9 只管学习与知识回写。这样下一个 Agent 能按 W 执行，同时 L0/L1 仍是唯一的抽象原则来源。

### 9. 小型项目管理嵌入现有工件，不另起 PMO

小型项目资料转译为现有工件的字段和门禁：W0/W1 写 goal、deliverables、acceptance criteria、non-goals、appetite；W2 用 OpenSpec 承接边界、风险和计划粒度；W4/W5 用小批量与验证证据控制返工；W6/W7 写发布、运行、责任和副作用边界；W8/W9 写 closeout、经验、证据和维护节奏。WBS 保持为交付物视图，OpenSpec `tasks.md` 保持为实现任务视图，避免重复维护。

### 10. 触发专项接专项执行条款，不上移技术细节

30 个 L3 触发专项仍然保留各自技术栈和治理主题，不把它们上移到 L0/L1。每个专项只新增一段“专项承接 L0/L1 与小型项目管理”：说明该专项的工件如何成为 task packet、DoD、write scope、验收证据、升级队列、失败分类账、release/operate closeout 或 handoff。这样多 Agent 执行者可以在命中专项后直接知道可并行读什么、必须串行写什么、哪些动作必须按 T2/T3 人审处理。

## 与现有资产的关系

- 总控 Agent / 角色 Agent 术语保留；编排规范给它们补契约。角色泳道 = worker 的专业化配置（persona + 读取清单 + 输出契约）。
- OpenSpec change 仍是工作单元载体；任务契约挂在 change 之下，一个 change 可拆多个任务契约。
- 人审点清单保留并升级为"升级队列"消费的事件类型。

## 备选方案与否决理由

- 备选：新建 `docs/A0-agent-orchestration/` 目录 + 在 10 个 W 主入口和 30 个专项加完整编排上下文块。否决：文件和重复过多，与"降复杂度"诉求相反；本轮只在 W 主入口和专项保留阶段/专项执行钩子，上下游契约仍在 L1 一处定义。
- 备选：直接把方法论写进 README。否决：README 是路由入口，混入长文会破坏"不要扁平清单"的既有约束（校验脚本强制 README 规范引用 ≤8 个）。
- 备选：立即定义 status.json 的完整 JSON schema 并写校验工具。否决：先立规范跑一个 change 验证字段集，再工具化，避免过早固化格式。
