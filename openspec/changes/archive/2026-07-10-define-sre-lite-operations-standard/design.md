# 设计：SRE-lite 运维规范

## 设计决策

### 1. SLO 是运维事实来源

一人公司不能同时追踪几十个指标。每个服务先用一个用户可见 SLO 连接用户影响、监控、告警和发布风险，避免 dashboard 看起来丰富但无法决策。

### 2. JSON SLO 文件优先

`ops/slo/<service>.json` 可被脚本检查，也适合后续生成 dashboard、runbook 链接或告警配置。Markdown 适合解释，JSON 适合做最低门禁。

### 3. 告警必须能行动

告警不以“指标异常”为充分条件，而以用户影响、error budget 消耗和 runbook 动作为升级条件。没有 runbook 的告警不能成为 page。

### 4. 不默认 24/7 pager

一人公司长期 24/7 值班不可持续。只有在付费用户、合同义务、收入风险或高影响安全/数据风险出现时，才升级响应模型。

### 5. 发布安全比发布仪式重要

发布 checklist 只保留测试、迁移、回滚、observability、smoke test 和发布后观察。复杂 CAB、多人审批和大型 release train 不适合一人公司默认流程。

### 6. 事故复盘必须产生行动项

无责复盘不是长文档，而是把影响、时间线、根因/触发因素和最多 3 个行动项记录下来。没有 owner/due/tracking 的行动项不算完成。

## 取舍

- 只要求 1-2 个 SLO 会漏掉部分内部风险，但能保证开始阶段可维护。
- JSON 对人类编辑略硬，但换来可检查和可自动化。
- 不默认 24/7 会牺牲极端响应速度，但保护单人长期产能。
- 不绑定监控 backend 会让第一版较抽象，但避免过早锁定云厂商或平台。
