## Context

唯一执行依据是 `docs/superpowers/specs/2026-07-15-rd-standards-content-rewrite-plan.md`。Change A `build-rd-rewrite-guardrails` 已完成工具建设，用户于 2026-07-16 明确要求继续整体修改，G1 已通过，治理状态为 `tooling_ready`。

本 change 是 Standard 文档与治理重构。W0–W9 是唯一主要内容来源；其他入口、历史 change、review、skill 和工具只能用于查漏、验证和治理，不能代替完整来源 review，也不能成为新原则来源。

## Goals / Non-Goals

**Goals:**

- 对 40 个 W0–W9 文件逐文件、逐非空行形成可审计覆盖。
- 将每个可独立保留、重写、合并、拆分、替代或退出的判断记录为原子规则。
- 为每条规则给出唯一主要归属，并保持跨项影响和冲突可见。
- 形成四分类、十一项、十五份原则列表和固定章节结构的并行草稿。
- 让覆盖、冲突、退出、复制和原则支持都能由工具复算。

**Non-Goals:**

- 不修改旧规范、正式导航或生产系统。
- 不追求按文件数或行数压缩；只消除无价值重复并保留必要边界。
- 不用机器检查替代用户语义判断，不把生产者自检称为独立终审。
- 不执行最终迁移或 Git 发布动作。

## Decisions

### 1. 先账本后草稿

按 W0–W2、W3–W4、W5–W6、W7–W9 四批完整读取。每批先更新 `source-inventory.csv`、`source-segments.csv` 和 `atomic-rules.csv`，并通过来源、范围、清单、分段和规则检查；四批完成前不形成全局原则。

### 2. 每个非空来源行恰好覆盖一次

分段账本使用连续行区间。`rule-bearing` 分段必须引用真实原子规则；上下文、示例、导航、重复和空段必须说明不形成规则的原因。逐行覆盖证明处理完整性，但不声称语义判断自动正确。

### 3. 主要归属由首次影响的研发决定确定

每条规则只能有一个四分类/十一项主要归属；跨项影响记录为 secondary，不复制规则。无法机械确定的冲突保持 `conflict` 并由用户在 G4 决定。

### 4. 重写保持约束，不保持旧表述

保留规则使用稳定目标规则 ID 追溯；合并、拆分、替代和退出保留来源映射与理由。规范化后不少于 40 字符的完整复制阻断，高相似文本进入人工审查。工具、框架和目录细节保留在执行细则，不上升为稳定原则。

### 5. 原则从规则簇产生

先形成十一项项目原则，再形成四分类原则。每个项目至少有可追溯的项目原则，每个分类至少有跨两个项目的分类原则；原则必须说明决策价值和更换技术后的稳定性。

### 6. 旧规范与草稿并存

`rebuild-draft/` 使用方案固定目录与章节；旧 W0–W9 和正式入口始终不变。G8 只表示审查包就绪，不表示迁移完成。G9 最多授权另行设计迁移方案。

### 7. 状态和人工决定只有一个权威入口

`tasks.md` 记录 change 任务进度；`governance/rd-standards-rebuild/run-state.json` 由 gate 独占写入；规则和原则事实位于草稿账本；人工决定追加到 `approvals.jsonl`，不能手工伪造状态。

## Risks / Trade-offs

- [来源规模大导致漏读] → 用逐行分段覆盖、四批 gate 和来源哈希阻断。
- [重组时悄悄丢失边界] → 每条原子规则必须有处理状态和目标/退出理由，覆盖矩阵复算。
- [新结构看似简洁但语义不正确] → G4、G6、G9 保留用户决定；工具只判定结构事实。
- [并行处理造成重复或冲突] → 来源批次可并行只读分析，但权威账本由单一控制者顺序合并并逐批验证。
- [内容阶段修改工具以迎合结果] → G2 冻结工具 manifest，content scope 同时检查工具文件和 manifest 身份。
- [旧审查快照与当前工作树不一致] → 作为已知旧治理限制保留，不修改其历史结果，也不把它当作本 change 内容来源。
