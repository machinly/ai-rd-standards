# 设计：W0-W9 主线 + 角色泳道

## 核心模型

W0-W9 和角色泳道不是两套流程，而是两个坐标：

- W0-W9 定位工作状态：是否该做、问题是否清楚、边界是否明确、是否实现、是否验证、是否发布、线上是否健康、是否学到东西、是否可维护。
- 角色泳道定位执行责任：产品、Tech Lead、后端、前端、测试、运维、运营、安全合规分别参与哪些 W、输出什么证据、何时升级给总控 Agent 或用户。

默认使用顺序：

1. 总控 Agent 先定位主导 W。
2. 根据主导 W 选择必须参与和可选参与的角色。
3. 每个角色 Agent 只读取 `docs/roles/<role>.md` 和当前 W 相关规范。
4. 总控 Agent 汇总冲突，更新 OpenSpec、tasks、索引或知识工件。
5. 用户只判断高影响事项。

## 角色列表

- Product：W0/W1/W8 主责，参与 W2/W5/W6。
- Tech Lead：W2 主责，跨 W0-W9 调度和冲突收口。
- Backend：W4 主责，参与 W2/W5/W6/W7。
- Frontend：W4/W5 主责，参与 W1/W2/W6。
- QA：W5 主责，参与 W2/W3/W4/W6/W8。
- Ops：W6/W7 主责，参与 W4/W5/W8/W9。
- Support Ops：W6/W8 主责，参与 W0/W1/W6/W9。
- Security Compliance：W2/W5/W7 主责，参与 W3/W4/W6/W9。

## 角色文档结构

每个 `docs/roles/*.md` 使用同一结构：

```markdown
# <Role> 角色入口

## 职责

## 默认参与的 W

## 必须参与的触发条件

## 默认读取

## 固定输出

## 交给总控 Agent 的情况

## 必须问人的情况
```

角色文档只做入口和调度，不复制专项规范正文。

## 多 Agent 输出契约

总控 Agent 输出：

- 当前主导 W。
- 参与角色。
- 本次需要读取的规范。
- OpenSpec/change/tasks 更新。
- 冲突和人审点。
- 下一步。

角色 Agent 输出：

- 角色判断。
- 读取的规范。
- 产出的 artifact 或检查结果。
- 风险、缺口和需要交给总控的事项。
- 是否需要人审。

## 专项精简目标

精简后的专项分为三类：

- 保留：高频角色工作或高风险门禁，需要独立文档。
- 合并：多个专项共享同一角色、同一门禁或同一最小工件。
- 降级：低频场景，只在父级 `00-main.md` 中保留触发提醒和人审点。

目标不是追求最少文件，而是让每个文件都有明确角色消费者和执行价值。

## 预期文档入口

调整后支持两种读法：

```text
按流程读：
README -> docs/00-start-here.md -> 当前 W -> 触发专项

按角色读：
README -> docs/03-role-index.md -> 当前角色 -> 当前 W 相关规范
```

## 校验方向

更新 `tools/verify_workflow_index.py` 或新增轻量校验，覆盖：

- `docs/03-role-index.md` 存在。
- 每个角色入口存在，并链接到至少一个 W。
- 角色入口不复制大量规范正文。
- `docs/02-standard-index.md` 中被引用的专项路径真实存在。
- 删除或合并专项后，索引无死链。
- README 同时指向流程入口和角色入口。

## 取舍

- 保留 W0-W9 作为主线，避免回到瀑布式角色流程。
- 给人一个熟悉的角色入口，降低第一次阅读成本。
- 通过角色消费者判断专项价值，减少“为了完整性而存在”的规范。
- 先用 Markdown 维护角色入口，不引入新工具。
