# 用户中心重建试验方案（第二轮）

状态：待在新的 Codex 会话中执行。

## 1. 试验目标

从零建设一个用户中心，并用真实建设过程再次检验当前研发规范。

本轮有两个目标：

1. 形成一个可供其他业务服务调用的用户中心；
2. 验证当前“Quick / Standard / High-risk + 最小研发内核”能否避免上一轮出现的问题，并以更少的流程负担获得可验证、可恢复的结果。

第二个目标是本轮试验的核心。功能完成不等于规范有效，结构检查通过也不等于产品完成或系统可发布。

## 2. 本轮与上一轮的关系

- 新项目必须在独立空目录中创建，不恢复、复制或依赖旧用户服务的代码、配置、数据库和未提交状态；
- 上一轮仅作为失败基线，允许引用其终止复盘和已经回灌到研发规范的事实；
- 本轮是路线 B 的重新运行样本，用来观察整改是否生效，不伪装成路线 A，也不能单独完成整个 A/B pilot；
- 本轮开始计量后才记录数据，不从聊天或上一轮记录中补造缺失数字。

## 3. 产品范围

### 登录与身份

- 支持微信、QQ、支付宝、Google 等通用登录方式；
- 登录 provider 使用可扩展适配层，后续可以接入 Firebase 或其他托管身份服务；
- 使用稳定的内部用户 ID，与任何外部 provider 身份解耦；
- 支持一个用户绑定多个外部身份，并处理绑定、解绑、重复身份和账号冲突；
- 支持注册/首次登录建号、必要的验证、账号恢复、session/设备管理和退出撤销。

### 用户中心能力

- 作为其他业务服务的统一用户中心；
- 提供稳定、版本化的服务调用 API；
- 支持服务/应用注册、调用凭据、scope、轮换和调用审计；
- 支持用户状态、基础资料、身份绑定和必要的下游事件；
- 统计区分产品指标、运行指标以及安全/审计指标。

### 后台管理与权限

- 后台管理员与普通用户使用不同的身份边界；
- 管理端具有独立登录入口、session 或 token audience、权限策略和审计；
- 不使用普通用户表上的单一 `is_admin` 字段作为权限模型；
- 支持用户查询、禁用/恢复、session 撤销、身份问题处理和权限管理；
- 高风险管理操作必须有确认、审计以及回滚或补偿方案。

### 两个前端

- 用户登录与自助前端：登录、回调、身份绑定、资料、session/设备和账号安全；
- 后台管理前端：用户、权限、安全事件和审计管理；
- 两个前端是独立安全表面，不能只靠隐藏按钮或前端路由区分权限。

### 容易遗漏但需要纳入设计的能力

- MFA/passkey，至少优先覆盖管理员；
- 账号导出、注销、删除传播、保留期和审计保留边界；
- 登录异常、账号枚举、撞库、限流和 provider 故障降级；
- 身份变化、安全事件和管理员操作通知；
- 健康检查、关键告警、备份与恢复。

以上能力不要求全部进入首个 MVP，但必须明确哪些本轮实现、哪些只保留扩展边界、哪些暂不做。

## 4. 已确认的工程约束

- 后端使用 Go、Kratos、Protobuf/gRPC；数据库使用 MySQL，数据访问使用 sqlc；
- 后端新项目必须从批准的 Kratos CLI 模板生成，不手工拼脚手架；未来批准自有应用模板后可替换；
- 两个前端使用经确认的 Vite + React/TypeScript 模板创建；
- 每个新应用记录模板名称、版本或 revision、创建命令和首次 build/test 结果；
- SQL 尽量使用 MySQL/PostgreSQL 都容易迁移的通用写法；必须使用厂商特性时隔离并记录原因和替代路径；
- 默认不使用 foreign key。引用完整性由非空/唯一约束、事务、幂等、应用逻辑、删除/补偿策略、孤儿扫描和并发测试保证；
- 本轮先采用模块化单体，不为试验主动拆分微服务，也不自行实现 OAuth/OIDC 的密码学核心。

## 5. 完整本地环境

项目必须提供统一、可重复的本地集成入口，覆盖：

- 用户中心后端；
- MySQL；
- 登录/用户自助前端；
- 后台管理前端；
- 必要的登录 provider mock。

统一入口至少支持启动、等待就绪、smoke、日志定位和清理。前端日常测试可以在宿主机运行，不要求专门制作容器镜像；但完整集成验收必须实际启动并访问两个前端，不能把“数据库和 mock 在容器中”称为完整环境。

验证证据分别标记为 unit、component、host integration、dependency container、complete local integration、browser E2E、provider sandbox 或 production observation，不能用较窄证据替代较宽结论。

## 6. 新会话开始前需要用户确认

执行会话先一次性确认以下产品决定，再进入生产性代码、migration 或稳定 API：

1. 首发市场以及第一个真实登录 provider；
2. 自主管理身份核心，还是优先采用 Firebase/其他托管 IdP；
3. API 初期仅供第一方服务，还是开放第三方；
4. 第一版是否支持组织/租户；
5. 管理员的身份来源，以及是否强制 MFA/passkey；
6. 用户数据地域、保留期、导出/删除和统计隐私边界；
7. 本轮两个前端的批准模板来源。

在这些决定未确认前，只允许整理权威产品输入、体验流程、验收映射和不可发布原型，不能由 AI 自行补齐高影响产品决策。

## 7. 研发规范执行方式

- 整个项目按 High-risk 管理，因为涉及身份、权限、管理员能力和个人数据；
- 只使用一份权威产品/体验/验收文档和每个实际批次的一份短 work brief，不默认创建 W0-W9 或 OpenSpec 四件套；
- OpenSpec 仅在身份协议、稳定契约或跨会话复杂设计确实因此减少歧义时使用，并记录它是否产生净收益；
- 身份模型、管理员边界、数据删除和难回退 API 在实现前由未参与设计的 reviewer 独立审查；
- 每个批次由生产者自检，项目完成后再由未参与产出的 reviewer 做独立终审；同一会话的第二遍自检不算独立审查；
- stopped 和 terminated 是合法状态。证据不足、门禁失败或方向未确认时停止，不为追求“完成”绕过规则。

建议按真实价值分批推进：项目基线与产品确认、身份核心与首个 provider、session 与用户前端、服务 API、管理员边界与后台前端、统计/安全/数据生命周期、完整验收。具体批次数可以在执行中调整，不为凑实验数量人为拆任务。

## 8. 试验记录

新项目维护 `experiments/rd-standard-pilot.jsonl`，每个真实任务遵循研发规范仓库的 `experiments/rd-pilot-record.schema.json`。

至少记录：

- task、project、comparison group、路线、风险和实际状态；
- 来源证据及模型、skill、CLI、模板和工具版本；
- 起止时间、冷启动时间、初始上下文量及单位；
- 人工中断次数与分钟、流程维护时间、总耗时、返工和首次通过；
- 工具调用、失败重试、token/成本和新增治理工件数；
- 实际运行的分层验证、独立审查发现、高风险漏检和剩余风险；
- 无法获得的指标及原因，不能把未知值记为 0；
- 可安排时进行一次延迟恢复演练，记录新会话恢复所需时间和上下文。

本轮至少在以下位置做检查：首个有效实现批次后、身份/管理员设计审查后、完整本地集成首次运行后、浏览器 E2E 后和独立终审后。

## 9. 本轮判定

本轮重点判断上一轮暴露的五类问题是否真正消失：

1. 是否先有经人确认的产品输入和体验设计，而不是用 work brief 代替；
2. 是否从批准模板真实生成，并保存可复查的 provenance；
3. 是否存在包含后端、MySQL、两个前端和 provider mock 的完整本地环境；
4. 是否准确区分验证层级，并实际完成需要的浏览器 E2E；
5. 身份、数据和管理员高风险设计是否在实现前独立审查，而不是只在末尾发现问题。

同时观察人工中断、恢复时间、总交付时间、流程耗时、返工和高风险漏检。达到单项目目标只能说明本轮整改得到一次正向证据；整个研发规范是否优于旧路线，仍以总 pilot 的跨项目 A/B 配额和聚合阈值为准。

## 10. 交付给新会话的指令

新会话读取本方案后，先确认项目目录为空、当前 runtime skill 与研发规范一致，并开始记录第一条 pilot 数据。随后只提交一份简短的产品决策请求，不先生成业务代码。用户确认第 6 节的决定后，再形成权威产品/体验/验收文档并进入实现前独立审查。
