# 用户中心项目方案（研发规范试验）

状态：历史试验输入；对应用户服务已删除，不再执行或恢复。仅用于解释当时计划测试什么。

## 1. 核心目标

建设一个可供多个业务服务复用的用户中心，同时把整个建设过程作为研发规范的真实试验。

项目目标有两层：

1. 交付一个安全、可扩展、可运维的用户中心；
2. 验证“Quick / Standard / High-risk + 最小研发内核”是否比原 W0-W9 默认流程更省注意力、更容易恢复，并且不增加高风险遗漏。

第二层是本项目的核心试验目标。不能因为功能完成就自动宣布规范有效。

## 2. 已确认需求

### 登录方案

- 支持微信、QQ、支付宝、Google 等常见第三方登录；
- 登录 provider 使用可插拔适配器，不把具体厂商逻辑写入用户核心领域；
- 后续可以接入 Firebase Authentication 或其他托管身份服务；
- 内部 `user_id` 必须稳定，不能直接使用微信 OpenID、Google `sub` 或 Firebase UID 作为主身份；
- 一个用户可以绑定多个登录身份，并支持安全的绑定、解绑和冲突处理。

### 用户中心核心能力

- 统一保存用户账号状态、基础资料和外部身份绑定；
- 为其他业务服务提供稳定 API；
- 支持服务/应用注册、调用凭据、scope 和凭据轮换；
- 支持登录、用户、服务调用和安全事件等统计；
- 用户中心负责身份与粗粒度 scope，业务资源的细粒度权限仍由各业务服务负责。

### 后台管理与权限

- 后台管理员和普通用户必须使用不同的身份边界；
- 不使用普通用户表上的单一 `is_admin` 字段作为安全模型；
- 管理端使用独立登录入口、token audience/session、权限策略和审计日志；
- 管理操作至少覆盖查询、禁用/恢复用户、查看身份绑定、撤销 session 和处理账号问题；
- 删除、合并、跨用户访问、权限变更等高风险动作需要明确确认、审计和回滚/补偿方案。

### 两个前端

- 登录与用户自助前端：登录、回调、账号绑定、基础资料、session/设备查看和账号安全；
- 后台管理前端：用户查询、状态管理、权限管理、安全事件和审计查询；
- 两个前端分别部署，不能只依靠前端路由或隐藏按钮区分权限。

## 3. 补充的常见能力

以下是原始需求中容易遗漏、但用户中心通常需要考虑的能力：

- 注册、协议/隐私同意和首次登录建号；
- 邮箱/手机验证、账号恢复和新设备提醒；
- 多身份绑定、解绑、账号合并以及重复账号冲突处理；
- session 管理、单设备退出、全部设备退出、token 撤销和密钥轮换；
- MFA、passkey 等增强认证能力，至少为管理员预留；
- 用户状态：pending、active、suspended、deletion_pending、deleted；
- 用户资料导出、账号注销、删除传播、保留期和审计保留边界；
- 下游服务同步事件，如 user.created、user.updated、user.disabled、user.deleted；
- 防撞库、限流、异常登录、账号枚举防护和 provider 故障降级；
- 通知能力：登录异常、身份绑定变化、管理员操作和安全事件；
- 备份恢复、健康检查、关键告警和第三方 provider 可用性监控。

统计必须拆成三类，不能混在一张“大盘”里：

- 产品统计：注册、登录转化、活跃用户、provider 使用比例；
- 运行统计：成功率、错误率、延迟、provider 故障、token/session 数量；
- 安全与审计：失败登录、权限拒绝、管理员动作、账号状态变化。审计日志不能当普通产品埋点处理。

## 4. 建议的范围与阶段

### MVP

- 使用当前批准的 Kratos CLI 模板生成模块化单体后端，保留 CLI/template provenance 和首次构建证据；未来批准自有应用模板后改用自有模板，不手工拼装根项目；
- 一个 MySQL 数据库，数据访问使用 sqlc；
- provider adapter 接口和一个真实 provider 的完整登录闭环；
- 稳定内部用户 ID、用户资料、身份绑定、session 和退出；
- 供第一方服务调用的用户查询 API 与应用注册；
- 普通用户与管理员身份隔离；
- 登录前端和管理前端；
- 最小审计、运行指标、限流和备份路径。

### 后续阶段

- 增加微信、QQ、支付宝、Google 等更多 provider；
- Firebase 或其他托管 IdP 适配；
- 账号合并、MFA/passkey、设备管理和异常登录检测；
- 用户导出/删除传播、事件订阅和更多统计；
- 确有需求时再增加多租户、公开第三方开发者平台或复杂 ABAC。

### 暂不做

- 自己从零实现密码学、OAuth/OIDC 协议核心或通用 IAM 平台；
- 一开始拆成多个微服务；
- 一开始支持所有 provider；
- 把所有业务服务的资源级权限都集中到用户中心；
- 企业级 BI、复杂风控平台或无人值守管理员操作。

推荐技术方向是 Go + Kratos + MySQL/sqlc，浏览器侧使用两个独立的 Vite + React/TypeScript 应用。数据库默认不建 foreign key；跨表完整性由应用层校验、事务、幂等、唯一/非空约束、删除策略、补偿任务和一致性扫描承担。SQL 尽量使用 MySQL/PostgreSQL 通用语法，确需数据库专有函数、类型或操作符时隔离并记录原因和替代路径。

### 完整本地环境

- 项目必须提供一个统一入口，从干净状态启动后端、登录/用户前端、后台管理前端、MySQL 和必要的 provider mock；
- 统一入口还要覆盖 readiness、smoke、日志定位和清理，不能要求执行者在多份聊天或临时命令中手工拼环境；
- 前端日常开发与测试可以运行在宿主机 dev server，不要求为此制作容器镜像；
- 完整集成测试时两个前端必须真实启动并可访问，后端与 MySQL/provider mock 也必须就绪；只有数据库、mock 或宿主机单服务的测试不得称为完整集成；
- Compose、脚本或任务运行器均可，但组件清单、端口、健康条件、启动顺序和停止方式必须进入仓库。

## 5. 开工前需要确认的决策

新会话开始后，先让用户确认以下事项，其余细节默认推进：

1. 首发市场是中国、全球还是同时覆盖；这决定第一个登录 provider；
2. 用户中心是自主管理身份核心，还是优先使用 Firebase/其他托管 IdP；
3. API 初期只供第一方服务使用，还是需要开放给第三方；
4. 是否从第一版支持组织/租户，还是只支持个人用户和多个应用；
5. 管理员使用什么身份来源，是否强制 MFA/passkey；
6. 用户数据地域、保留期、注销/导出和产品统计的隐私边界。

推荐默认：先服务第一方系统；选择一个目标市场最常用 provider；管理员独立登录并强制增强认证；内部用户 ID 与任何外部 provider 解耦。

## 6. 建议执行批次

新项目可以按以下真实任务推进，但不得为了满足试验数量而故意降低风险等级：

1. 项目骨架与关键架构决定；
2. 用户、身份绑定和账号状态模型；
3. provider adapter 与第一个登录 provider；
4. session/token、退出和撤销；
5. 登录与用户自助前端；
6. 服务 API、应用注册和调用凭据；
7. 管理员身份、RBAC、管理 API 和审计；
8. 后台管理前端；
9. 运行指标、产品统计和安全事件；
10. 第二个 provider、账号绑定/冲突处理；
11. 导出、注销、删除传播和发布准备。

第 1 批必须先证明：Kratos CLI 模板来源可追溯、MySQL/sqlc 基线可构建、两套前端存在，以及完整本地环境能统一启动和清理。没有这组证据，不进入后续身份实现。

每个批次只保留一份 work brief。只有 API 行为、身份安全或跨会话设计确实需要更强规格时才使用 OpenSpec，不按任务时长触发。

## 7. 研发规范试验方案

### 试验路径

- 本项目使用路线 B：Quick / Standard / High-risk + 最小内核；
- 当前方案任务记为 High-risk preparation，因为它涉及身份、权限、个人数据和管理员能力，但本阶段不执行生产副作用；
- 不并行制造一套 W0-W9/OpenSpec 实现；历史流程只作为已有基线，避免为了试验重复开发；
- Standard/High-risk 批次完成后由未参与产出的另一个会话或模型做独立终审。

### 每个真实任务需要记录

统一写入新项目的 `experiments/rd-standard-pilot.jsonl`，每项至少记录：

| 字段 | 含义 |
| --- | --- |
| task_id | 稳定任务编号 |
| risk_path | Quick / Standard / High-risk |
| outcome | 期望结果 |
| started_at / finished_at | 起止时间 |
| startup_minutes | 到首个有效动作所需时间 |
| context_lines_or_tokens | 初始读取上下文量 |
| artifacts_created | 新建治理工件数量 |
| process_minutes | 维护方案、brief、审查等流程耗时 |
| human_interruptions | 需要用户决策的次数及原因 |
| verification | 实际运行的测试、构建、检查和人工验收 |
| first_pass | 首次验证是否通过 |
| rework_count | 返工次数和原因 |
| high_risk_miss | 是否漏掉身份、权限、数据或生产风险 |
| reviewer_findings | 独立 reviewer 发现的问题 |
| residual_risks | 剩余风险和下一步 |

另外记录每次规范或 skill 产生的冲突。例如本次已发现：旧 Go/Vite skill 会按任务时长要求 OpenSpec，与当前最小内核冲突；执行时应记录“未采用旧时长门槛”的理由。

### 试验检查点

- 第 3 个任务后：检查启动阅读量、用户打断和流程耗时；
- 第 5 个任务后：做一次中断恢复，让新会话只凭 brief 恢复工作；
- 第 10 个任务后：汇总全部指标并做独立 review；
- 如果出现身份串号、越权、管理员边界混淆、账号错误合并或敏感数据泄漏，视为高风险漏检，不能用功能完成抵消。
- 如果应用不是从批准模板生成，或者完整本地环境缺少任一前后端/依赖却宣称集成完成，同样记录为流程失败而不是普通待办。

### 成功条件

相对于当前历史基线：

- 人工中断和恢复时间下降至少 30%；
- 总交付时间增加不超过 10%；
- 流程维护时间没有超过实现收益；
- 高风险漏检不增加；
- 返工率不增加；
- 新会话能够在 15 分钟内从一份 brief 恢复当前状态。

未达到条件时，应删减或修改规范，不增加更多文档来解释失败。

## 8. 处置边界

本方案不再是新会话启动文本。对应用户服务已经删除，不恢复代码、环境或未完成批次，也不继续评价该服务的产品完成度。后续只从本方案与终止复盘中提取研发规范的验证事实：模板来源、产品输入、完整本地集成、证据层级、审查时机、运行时 skill 一致性和可测量性。
