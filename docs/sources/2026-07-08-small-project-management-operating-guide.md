# 小型项目管理操作指南草案

状态：历史研究草案，不是正式规范，也不证明 W0-W9、OpenSpec 或固定时长门槛有净收益。当前默认规则以 `docs/01-minimal-rd-kernel.md` 为准。

日期：2026-07-08

## 目的

本文整理“小型项目管理”的候选做法，保留为来源研究和历史设计依据。这里的小型项目管理不是企业 PMO 的缩小版，而是给一人公司、小团队和 AI 辅助研发参考的轻量管理动作；是否采用应由任务影响、可逆性和实测净收益决定，不能因为本文存在而自动生效。

来源限制：下列资料可以支持“小项目需要可裁剪的目标、范围、风险和验收管理”，但不直接证明 W0-W9、半天阈值、强制 WBS 或默认 OpenSpec 是本仓库的最佳方案。

核心目标：

- 明确这件事为什么做、做到什么算完成。
- 把范围拆成少量可交付、可验收、可暂停恢复的工作包。
- 控制范围蔓延、依赖遗漏、验收不清和中途失焦。
- 用最少工件保留关键上下文，而不是维护厚重项目计划。

## 什么算小型项目

满足多数条件时，可以按小型项目管理：

- 周期通常在几天到数周内，而不是季度级或年度级。
- 参与者少，通常是一人到少数几人。
- 目标较单一，最终交付物可以说清楚。
- 范围较窄，依赖数量可控。
- 决策人明确，验收人明确。
- 失败影响可控，不涉及重大合同、安全、隐私、财务或生产不可逆风险。

不应按小型项目处理的情况：

- 跨多个团队、供应商或长期路线图。
- 交付物复杂到无法用一页范围说明讲清。
- 有重大安全、隐私、合规、合同、计费或客户承诺风险。
- 需要长期运行、持续预算或多阶段组织变更。
- 决策人、验收标准或停止条件不明确。

重要判断：小项目可以很小，但不一定低风险。风险高时，仍要补安全、隐私、发布、回滚或合规门禁。

## 小型项目管理的最小原则

1. 先定义项目，再拆任务。

   不要从任务清单开始。先写清目标、交付物、验收标准、非目标、约束和停止条件。

2. WBS 拆交付物，不拆动作。

   WBS 的一级节点应是可验收产出，例如“范围确认”“接口契约完成”“验证通过”“上线准备完成”。不要写成“开会”“沟通”“开发”“测试”。

3. 时间固定，范围可变。

   小项目最容易被“顺手加一点”拖大。先给 appetite，再按 appetite 缩范围。

4. 工件少，但必须能恢复上下文。

   最小工件应回答：为什么做、做什么、不做什么、谁负责、如何验收、当前阻塞、下一步是什么。

5. 控制变更，不控制人。

   小项目不需要复杂审批，但任何新增范围都要问：是否改变目标、是否超过 appetite、是否影响验收、是否需要重新拍板。

6. 收尾和停止同样重要。

   小项目不只以“完成”结束，也可以以“停止”“停车”“转为更大项目”“回到发现阶段”结束。关键是记录原因和下一步。

## 操作流程

### 1. 入口判断

先判断这是不是一个项目，而不是日常任务。

可以用三个问题：

- 是否有明确目标和交付物？
- 是否需要协调范围、依赖、时间或风险？
- 是否需要在未来恢复上下文或向别人说明进展？

如果三个问题至少两个为“是”，就按小项目处理。

入口产出：项目卡片。

### 2. 启动

启动阶段只做一件事：把模糊请求变成可判断的项目。

必须写清：

- 背景：为什么现在要做。
- 目标：达成什么结果。
- 交付物：最终会留下什么。
- 验收标准：谁用什么证据判断完成。
- 非目标：哪些东西明确不做。
- 约束：时间、成本、技术、合规、人员、客户承诺。
- 决策人：谁能扩大、缩小、停止或验收项目。

启动阶段的出口：

- `go`：可以进入计划。
- `needs-clarity`：目标、验收或边界不清，先补信息。
- `park`：有价值但现在不做。
- `kill`：不值得继续。

### 3. 规划

规划阶段的顺序：

1. 写范围说明。
2. 写 WBS。
3. 从 WBS 派生行动计划。
4. 记录风险、问题和沟通节奏。

不要直接从行动计划开始。行动计划回答“怎么做”，WBS 回答“要交付什么”。如果没有 WBS，任务清单很容易变成忙碌记录。

### 4. WBS 分解

WBS 的推荐层级：

```text
项目目标
  1. 一级交付物
     1.1 工作包
     1.2 工作包
  2. 一级交付物
     2.1 工作包
```

小项目默认不超过三级。一级交付物建议 2 到 7 个；超过 7 个，通常说明范围太大，应该拆项目或收窄目标。

每个工作包必须满足：

- 有明确产出。
- 有验收证据。
- 有负责人或负责 Agent。
- 有依赖关系。
- 能估算投入。
- 能独立暂停和恢复。

工作包示例：

| 好的工作包 | 不好的工作包 |
| --- | --- |
| 明确支付失败重试策略并形成决策记录 | 讨论支付 |
| 完成 API 契约并通过兼容性检查 | 写接口 |
| 完成 10 条核心 eval case 并记录结果 | 做 AI 测试 |
| 完成上线清单、回滚路径和 smoke test | 准备发布 |

### 5. 行动计划

行动计划从 WBS 工作包派生，不直接替代 WBS。

每个任务至少包含：

- 任务名。
- 对应 WBS ID。
- 负责人。
- 截止或下一次检查时间。
- 当前状态。
- 阻塞。

任务粒度以“一次连续工作能推进”为准，不追求拆到分钟级。

### 6. 执行与控制

小项目的控制节奏要短：

- 每天或每个工作块结束时更新一次状态。
- 每周或每个关键节点做一次范围检查。
- 有阻塞就记录，不靠记忆。
- 有新增需求就进入变更判断。

状态更新只回答四件事：

- 已完成什么。
- 当前卡在哪里。
- 范围或风险是否变化。
- 下一步做什么。

### 7. 风险与问题

小项目不需要复杂风险系统，但必须区分风险和问题：

- 风险：可能发生，会影响目标。
- 问题：已经发生，正在影响目标。

每条风险或问题至少包含：

- 描述。
- 影响。
- 应对动作。
- 负责人。
- 何时复查。

常见风险：

- 目标不清。
- 验收人不明确。
- 外部依赖延迟。
- 技术方案不确定。
- 范围不断增加。
- 验证证据不足。
- 发布或回滚准备不足。

### 8. 变更控制

小项目的变更控制可以很轻，但不能没有。

任何新增范围都问：

- 它是否服务原目标？
- 是否改变验收标准？
- 是否超过 appetite？
- 是否增加安全、隐私、成本、合同或客户承诺风险？
- 是否应该另开一个项目？

默认规则：

- 不影响目标、不超过 appetite 的小调整，可以直接记录。
- 影响验收、时间、成本、风险或客户承诺的变化，必须由决策人确认。
- 如果变化让项目变大，先停止执行，重新做入口判断。

### 9. 收尾

收尾不是形式。它保护下一次接手。

收尾必须记录：

- 交付物是否被验收。
- 验收证据在哪里。
- 哪些内容没有做。
- 剩余风险是什么。
- 是否需要后续项目。
- 学到了什么。
- 相关文档、代码、配置或运行记录在哪里。

项目结束状态：

- `done`：完成并验收。
- `stopped`：主动停止，记录原因。
- `parked`：暂缓，记录恢复条件。
- `split`：拆成多个后续项目。
- `escalated`：升级为更大项目或正式变更。

## 一页检查清单

启动前：

- [ ] 目标明确。
- [ ] 交付物明确。
- [ ] 验收标准明确。
- [ ] 决策人明确。
- [ ] 非目标明确。
- [ ] appetite 明确。

计划完成前：

- [ ] WBS 是交付物分解，不是动作清单。
- [ ] 一级交付物不超过 7 个。
- [ ] 每个工作包都有验收证据。
- [ ] 任务都能追溯到 WBS。
- [ ] 风险和问题有负责人。
- [ ] 变更判断规则明确。

执行中：

- [ ] 状态更新包含 done、blocked、change、next。
- [ ] 新增范围经过判断。
- [ ] 阻塞没有只留在聊天里。
- [ ] 验证证据随做随记录。

收尾时：

- [ ] 交付物已验收或明确停止。
- [ ] 未完成项已记录。
- [ ] 剩余风险已记录。
- [ ] 后续动作已决定。
- [ ] 上下文可以被恢复。

## 历史映射（已退出默认规范）

以下内容记录 2026-07-08 时的设计意图，只用于追溯，不是当前路由或强制要求。

当时的映射设想没有把“小型项目管理”做成独立大体系，而是这样放置：

- W0：判断是否值得做、是否需要小项目计划、是否进入 now / next / parked / killed。
- W1：补用户问题、证据、成功指标。
- W2：把高影响项目转为 OpenSpec change，明确行为、边界、风险和退出条件。
- W3-W7：把 AI 行为、实现、验证、发布、运行准备作为 WBS 的交付物或工作包。
- W8：把结果、反馈和复盘转成下一步决策。
- W9：沉淀 WBS、验收证据、状态和上下文恢复入口。

推荐定位：

```text
历史设想：小型项目管理位于 W0 之后、W2/OpenSpec 之前或与其并行；当前三档路径不采用这条固定位置关系。
WBS = 交付物视图。
OpenSpec tasks.md = 实现任务视图。
decision-board = 取舍和优先级视图。
focus-review = 周期复盘视图。
```

这样可以避免三种问题：

- 把小项目管理变成重型 PMO。
- 把 WBS 和 OpenSpec `tasks.md` 重复维护。
- 把所有想法都伪装成项目。

## 历史候选规则（未纳入当前默认规范）

以下清单曾被提议纳入规范。它现在只作为试验候选，不具有 `MUST` 效力：

当时提议只保留以下规则：

1. 原提议：超过半天、跨多个 W、依赖较多或暂停后难以恢复的工作写小项目计划。当前规则只在确有恢复或验收需要时使用一份 work brief，时长本身不触发。
2. 原提议：小项目计划先写 goal、deliverables、acceptance criteria、non goals、appetite。
3. 原提议：WBS 面向交付物，而不是动作列表。
4. 原提议：每个工作包提供验收证据。
5. 原提议：新增范围经过变更判断。
6. 原提议：项目以 done、stopped、parked、split 或 escalated 之一收尾。

## 历史研究问题

- 是否后续要把小项目计划作为 W0 的触发专项。
- 是否后续要新增 `planning/wbs/<work-id>.md` 工件。
- WBS 与 OpenSpec `tasks.md` 的边界是否按“交付物视图 / 实现任务视图”区分。
- 哪些项目规模必须从“小型项目”升级为正式 OpenSpec change 或更大治理流程。
