# 研发规范重建设计

状态：待用户书面审阅  
日期：2026-07-15  
适用对象：一名产品/研发负责人 + Codex

## 1. 目标

把当前研发规范重建为一套可以快速理解、实际执行且低成本维护的工作方式：

- Superpowers 是研发执行方法，负责澄清、设计、计划、实现、调试、测试、审查和完成验证；
- OpenSpec 只在变更值得保留长期契约与状态时启用；
- 本仓库只保存两者之间的选择规则和本项目特有的安全边界；
- 删除未实际应用、重复表达或只证明格式完整的流程资产；
- 不兼容旧目录、旧路径或旧工作流。

## 2. 现状证据

当前工作树约有：

- `openspec/` 312 个文件、约 1.2 万行文本；
- `docs/` 59 个文件、约 7800 行文本；
- `tools/` 15 个文件，其中现有统计覆盖的 8 个工具约 3100 行；
- `reviews/`、`knowledge/`、`experiments/` 和 `decisions/` 保存了多套历史状态与解释；
- 工作树存在 373 项未提交变动，包括 122 项修改、232 项删除和 19 项新增或未跟踪文件。

主要问题不是缺少导航，而是同一规则同时存在于 README、最小内核、W0-W9、角色文档、skill、knowledge、OpenSpec 主规格和验证脚本。验证器还硬编码路径、固定措辞和历史文件，使精简本身变成失败条件。

## 3. 非目标

- 不建设虚拟研发组织或模拟产品、架构、测试、运维等角色；
- 不复制 Superpowers 已提供的通用研发技能；
- 不建立新的 W 阶段、成熟度模型、证据账本或治理目录；
- 不为未来团队扩张预留兼容层；
- 不把 OpenSpec 格式校验当作功能验收；
- 不在本次改造中提交、推送或覆盖现有未提交工作。

## 4. 核心模型

### 4.1 直接执行模式

适用于局部、可逆、能在当前上下文完成并验证的工作。使用相关 Superpowers 技能推进，不创建 OpenSpec。

典型工作包括只读分析、局部文档修改、小型重构、明确的缺陷修复和隔离环境中的实验。

### 4.2 契约执行模式

满足任一条件时创建 OpenSpec change：

1. 改变需要长期维护的产品行为、API、数据结构或 AI 行为；
2. 工作会跨会话，需要可靠恢复；
3. 存在多个重要验收条件或必须锁定的技术取舍；
4. 失败影响较大，需要明确停止条件和回滚方式。

OpenSpec 记录 outcome、non-goals、acceptance、关键设计、风险、回滚和当前状态。Superpowers 继续负责如何设计、实施和验证。

### 4.3 外部副作用确认

涉及生产、真实数据、资金、权限、凭据、对外通信或不可逆动作时，Codex 可以完成准备、实现、测试和演练，但执行真实副作用前必须说明：

- 将执行的具体动作和目标；
- 预期影响与影响范围；
- 验证和回退方式。

随后等待用户对该次具体动作的明确确认。OpenSpec、测试通过或先前的一般授权都不能替代这次确认。

## 5. 单一事实源

新体系只有 `WORKFLOW.md` 是规范性事实源：

- `README.md` 只解释用途并链接 `WORKFLOW.md`；
- `AGENTS.md` 只负责让 Codex 进入仓库时读取 `WORKFLOW.md` 并使用已安装的 Superpowers；
- OpenSpec change 只描述某次变更，不重述长期流程；
- 验证工具只检查可机械判断的结构、链接和内容预算，不检查固定措辞；
- 主题性工程知识由实际项目文档、官方资料和按需技能提供，不在本仓库复制。

## 6. 目标结构

```text
README.md
AGENTS.md
WORKFLOW.md
.gitignore
openspec/
  README.md
  config.yaml
  changes/              # 仅真实活动或仍有保留价值的 change
tools/
  check_workflow.py
.work/                  # 直接执行模式的临时设计/计划，gitignore
```

约束：

- 默认阅读只有 `README.md` 和 `WORKFLOW.md`；
- `README.md`、`AGENTS.md` 和 `WORKFLOW.md` 合计不超过 350 个物理行；
- 仓库不保留 playbook 索引、角色索引或知识副本；
- `.work/` 中的 Superpowers 临时工件完成后删除；
- 契约执行模式的设计和计划放在对应 OpenSpec change 内，避免第二份任务状态；
- `tasks.md` 只维护状态和下一步，详细实施步骤放在同一 change 的 `implementation-plan.md`。

安全规则合并进 `WORKFLOW.md`，不再单独创建 `SAFETY.md`，以避免一个规则形成新的入口。

## 7. 删除边界

以下内容从新工作树删除，历史仅由 Git 和改造前快照保存：

- `docs/W0-*` 至 `docs/W9-*`、角色文档、旧入口和实验性操作模型；
- `knowledge/` 全部副本；
- `reviews/`、`experiments/`、`decisions/` 的历史治理材料；
- `skills/one-person-openspec-rd/`，避免复制 Superpowers 和新工作流；
- 现有 56 份 OpenSpec 主规格和 60 份历史归档 change；
- 现有格式、pilot、runtime 同步、证据清单和固定措辞验证器。

若某条技术约束仍然真实适用于某个产品，应迁移到该产品仓库，而不是继续保存在通用研发规范仓库。

## 8. 迁移策略

### 8.1 保存现有工作

实施任何批量删除前，在工作区外创建带时间戳的完整快照，并保存：

- 当前 `git status`；
- tracked 文件的 binary diff；
- 未跟踪文件；
- 快照哈希和恢复说明。

快照验证可读取后才允许删除。整个改造不执行 commit、push、stash、reset 或 checkout。

### 8.2 重建顺序

1. 建立改造前快照并验证；
2. 写入新的 `WORKFLOW.md`、`README.md` 和 `AGENTS.md`；
3. 精简 OpenSpec 配置和说明；
4. 用一个小型检查器替换现有验证工具；
5. 删除旧目录和历史资产；
6. 运行结构检查和场景验收；
7. 比较改造前后的文件数、行数、入口数和任务判断成本。

## 9. 验证设计

### 9.1 机械检查

唯一命令：

```powershell
python tools/check_workflow.py .
```

它只检查：

- 必要入口存在；
- 本地 Markdown 链接有效；
- 规范性文档不超过内容预算；
- 已声明退出的旧顶层目录不存在；
- OpenSpec 配置可读取。

它不检查固定中文句子，不要求历史 review、manifest、角色、旅程或证据文件存在。

### 9.2 场景验收

从只读取 `README.md` 的冷启动上下文验证以下任务：

| 场景 | 预期选择 |
| --- | --- |
| 修正文档错字 | 直接执行 |
| 修复可复现的局部缺陷 | 直接执行，使用系统化调试和测试 |
| 新增长期维护的 API 行为 | 契约执行 |
| 跨会话的大型重构 | 契约执行 |
| 准备生产数据迁移 | 契约执行；真实迁移前等待确认 |
| 只读调查生产事故 | 直接执行；产生真实副作用前等待确认 |

每个场景必须在 60 秒内选对模式，且不需要读取旧 playbook。

### 9.3 精简指标

- `README.md`、`AGENTS.md` 和 `WORKFLOW.md` 合计不超过 350 个物理行；
- 默认阅读不超过 200 行；
- 新工作树文本总行数相对当前基线减少至少 80%；
- 只有一个规范性事实源；
- 只有一个验证命令；
- 六个场景全部正确分类；
- 验证器没有硬编码规范句子。

## 10. 风险与处理

- **误删现有未提交工作**：先做工作区外完整快照并验证恢复内容。
- **删掉仍有价值的技术约束**：只从通用规范仓库退出；产品仍需要的约束以后进入对应产品仓库。
- **OpenSpec 启用条件仍然模糊**：以四个可观察触发条件和六个场景测试校准。
- **Superpowers 产生新文档堆积**：直接模式使用 gitignore 的 `.work/`；契约模式把工件收口到 change。
- **验证器再次成为流程本体**：检查器只验证结构和预算，流程语义由场景测试证明。

## 11. 完成条件

只有同时满足以下条件才算完成：

1. 新结构已经落地，旧结构不再是活动入口；
2. 现有未提交工作有可验证快照且未被不可恢复地覆盖；
3. Superpowers 与 OpenSpec 的职责边界在唯一事实源中明确；
4. 六个场景全部通过；
5. 机械检查通过；
6. 文件数、行数和入口数达到精简指标；
7. 未执行 commit 或 push；
8. 用户能从 README 在一分钟内解释何时需要 OpenSpec。
