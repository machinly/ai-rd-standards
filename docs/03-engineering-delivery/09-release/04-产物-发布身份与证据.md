# 发布：产物、发布身份与证据

## 规范要求

<!-- rule-id: RELEASE-ARTIFACT-001 -->
### 只部署 CI 构建的不可变产物

production deploy 可以从本地触发，但待部署产物必须由 CI 从明确的源码 revision 构建并保持不可变；不得从开发机直接制作或修改线上 release。正式制品必须存入持久、可恢复的制品位置，按应用和版本唯一寻址，写入后不得覆盖或原地修改；临时目录、开发机工作区和应用仓库 Git 都不能充当 production 制品库。部署前后都校验内容摘要，当前版本、上一个兼容回退版本和所有实际进入 production 的版本不得被候选制品清理策略删除。回滚应重新部署已知的兼容 release set，而不是就地篡改正在运行的产物。单应用首版先建立最小可重复路径；只有多个应用已经共享发布机制或需要环境级版本组合时，才把公共能力提升为独立发布控制面。

<!-- rule-id: RELEASE-ARTIFACT-002 -->
### 建立可追溯的 release identity

每个应用制品必须有应用内唯一版本，并至少纳入源码 revision 与 artifact digest；能取得 source tree identity 时一并保存。每个 production 环境变更还必须有唯一 `release_id` 或 `release_set_id`，记录该环境选择的每个应用及其独立制品版本，不能假设同一环境的所有应用共用一个版本号。`main` 只表示候选可发布，不表示已进入生产；production 必须通过显式 trigger、tag、environment protection 或已验证的 preview promote 才能发生。

<!-- rule-id: RELEASE-ARTIFACT-003 -->
### 分离稳定定义、构建事实、环境选择与 run

应用 release contract 只声明该应用如何构建、产出、运行、配置、迁移、兼容、回退和验证，不写生产主机、真实 secret 值或某个环境的实际配置。`build` 从明确 revision 产出不可变 artifact，并生成 artifact manifest 记录本次实际源码身份、contract 版本与摘要、文件路径/大小/摘要、migration 和配置 schema 变化；环境 release set 负责选择目标环境中每个应用的制品版本；`run` 负责记录一次实际部署及其结果。四类事实用版本和内容摘要相互链接，但不得共用一个可覆写状态代替：contract 有效不等于 build 成功，build 成功不等于 release 获准，release 获准也不等于 run 已成功。

<!-- rule-id: RELEASE-EVIDENCE-001 -->
### 保存发布证据摘要

摘要必须同时给出主决定、`release_id` 或 `release_set_id`、当前与目标 release set 的差异、各应用 artifact manifest 引用、目标环境、gate 结论、smoke 结果、rollback 路径、watch plan 与残余风险。差异至少列明变化的应用及制品、migration、配置 key/schema、服务/端口/路由/依赖、预期停机、停止条件与回退边界；未变化项可按摘要引用而不重复抄写。AI change 在实现任务结束后还要更新 release note。准备交给运行阶段前，上述字段均须明确，且验证失败、accepted risk 和 skip 已被本次决定逐项承接。

<!-- rule-id: RELEASE-EVIDENCE-002 -->
### 保存实际 release run 记录

每次 run 记录 `release_id` 或 `release_set_id`、实际环境应用版本组合、每个变化应用的源码 revision 与 artifact digest 或 deployment URL、适用的 OpenSpec change id、实际执行的 migration 与配置 schema、各 gate 结果、部署时间与环境、执行器 recap、smoke 结果、观察到的 SLO/错误信号，以及是否回滚或下一动作。实际 release set 与 run record 共同构成环境部署事实源；服务器 `current` 链接、schema-version 文件、CI 状态和人工说明只能作为可核对的运行状态或证据，不得各自声称是另一份环境事实源。发布总日志还应保留最终结果和可执行的回退方式，不能只记录“已部署”。
