# 发布：发布流水线合同

## 规范要求

<!-- rule-id: RELEASE-PIPELINE-001 -->
### 按应用自治、按环境组合发布工件

每个可发布应用在自己的应用目录或仓库维护版本化 release contract、构建入口和应用特定 smoke/rollback 方法；contract 不得把其他应用或具体生产环境硬编码进来。单应用项目可在本仓库维护最小 pipeline、checklist 与 run record；当多个应用共享执行能力、需要独立版本或共同组成一个环境时，公共 contract schema、应用 catalog、环境 inventory/Application、release set、通用校验与执行入口、制品目录和发布记录必须由独立共享发布工程维护。共享工程是组织内公共能力，不要求公开或开源；应用仓库不得复制一套环境控制面。目标环境只保存已部署的不可变版本、环境配置与 secret、进程/路由配置、当前版本指针和运行状态，不反向拥有应用 contract 或发布控制面定义。所有工件采用其他落点时必须从发布清单提供可解析链接，production smoke 与 rollback 仍须指向可读、可执行的方法。

<!-- rule-id: RELEASE-PIPELINE-002 -->
### 让 OpenSpec 状态进入发布门禁

适用的 change 必须能定位 proposal、spec、design 与 tasks；未完成事项要明确完成或延后，不能从证据中消失。公开仓库或官方 SDK 的发布应使用独立 OpenSpec change。流水线至少保留 OpenSpec 类 gate，并在发布前确认 tasks 已完成或有明确延后结论。

<!-- rule-id: RELEASE-PIPELINE-003 -->
### 维持一人可执行的流水线边界

GitHub Actions 是默认 CI provider，而不是绑定；部署执行器也可按现有环境选用 Ansible 或等价工具，但必须消费版本化声明并保存实际结果，不能让散落脚本成为隐式控制面。普通小改可以自动部署到非生产环境，首次或高风险 production 仍保留 checkpoint。共享能力按实际 workload archetype 扩展，不得以应用名称增加条件分支；已支持类型的新应用如果仍要求修改通用执行逻辑，应先修正 contract 或抽象边界。Terraform 平台、真实 Kubernetes/GitOps、复杂多环境审批矩阵、企业发布列车或完整供应链合规，只有真实规模或合规要求出现后才另开 change；采用 Kubernetes 风格声明不等于要求使用 Kubernetes runtime。

<!-- rule-id: RELEASE-PIPELINE-004 -->
### 维护可判定的 pipeline schema

版本化发布 schema 必须能分别表达五类对象或语义等价物：应用稳定定义 `ApplicationReleaseContract`、构建事实 `ArtifactManifest`、环境无关应用注册 `ApplicationCatalog`、环境绑定 `Application`、环境版本组合 `ReleaseSet`。推荐采用 `apiVersion`、`kind`、`metadata`、`spec` 的声明式 envelope；实际结果写入 run record 或独立 status，不反写应用 contract。应用 contract 至少覆盖源码根、构建与工具链、制品布局/权限、运行命令与用户、端口/健康/资源、配置 schema 与 secret key 名称、migration/兼容/回退边界及应用 smoke；artifact manifest 至少覆盖源码 revision、contract 摘要、文件摘要/大小、migration 与配置 schema 变化；环境 Application 只绑定目标、非敏感配置与 secret reference；ReleaseSet 只选择各应用制品版本。pipeline 自身还要描述 owner、trigger、CI/执行器、required gates、strategy、production checkpoint、rollback、watch 与 provenance。项目可使用等价 schema，但这些语义、可读 smoke/rollback 和 production checklist 链接仍为最低要求；字段顺序不构成门禁。

<!-- rule-id: RELEASE-PIPELINE-005 -->
### 声明最低 gate 类别与等价命令

流水线必须包含适用的 contract/schema 校验、OpenSpec、test、artifact manifest/摘要校验、release set plan、目标环境 preflight、smoke 与 rollback 类动作；使用非默认 CI 或部署执行器时仍须提供语义等价的 gate。发布 Protobuf 契约时，把 `buf lint`、`buf breaking` 或作用等价的检查纳入 CI/release gate。命令不可执行、被跳过或结果过期时，按验证债务规则处理，不能把 gate 名称本身当作通过证据。

<!-- rule-id: RELEASE-PIPELINE-006 -->
### 固定默认 gate 顺序与失败处理

默认先完成“规范/contract 与生成差异检查 → test/eval/migration 风险检查 → build/security 与 artifact 入库”，再由唯一发布入口按“validate → plan → preflight → stage → configure → migrate → activate → supervise/route → verify → record → post-deploy watch”执行适用步骤；production 的 plan 与 preflight 之后、真实副作用之前保留人工 checkpoint。`plan` 必须比较当前与目标 release set 并列出制品、数据、配置、服务、端口、路由与依赖变化；任一实际变化不在已批准 plan 中时立即停止。阶段不适用时记录理由而不是伪造通过。任一 `required=true` gate 为 `fail`、`blocked`、未执行或结果过期时，停止后续晋级；只有完成重跑，或由有权的人按 accepted risk 合同承接后，才能产生新的 go/no-go 决定。下游结果依赖的 revision、contract、artifact、release set 或配置变化后，旧 gate 结果不得继续复用。

<!-- rule-id: RELEASE-PIPELINE-007 -->
### 按变更栈整合发布门禁

流水线按实际变更组合门禁：Go/Kratos/sqlc/gRPC 连接测试、race、生成差异、sqlc 与契约检查；Vite 连接锁文件安装、测试、production build 与 preview；用户可见 AI 连接 ready 样本、eval、高风险输入运行、版本与 fallback；SRE-lite 连接 release checklist、smoke、observability 与 rollback。每项都链接本文件对应细则与实际结果，未触发的栈不强行加入空 gate。

<!-- rule-id: RELEASE-PIPELINE-008 -->
### 维护唯一生产入口与受控迁移

pipeline 或 release checklist 必须写明唯一 production 入口、适用应用、所用 revision/contract/artifact/release set 和结果落点；仓库提供发布 skill 或本地检查脚本时，本地检查只作为可重复 preflight，不能替代 CI 中的 required gate。应用特定生命周期动作必须由应用 contract 显式声明并由公共入口调用，不能混入通用执行器的应用名称分支。直接 SSH 或等价远程 shell 默认只用于只读诊断；生产写操作必须回到声明式发布入口，只有明确应急授权、限定动作和执行记录时才能例外。旧入口或重复脚本只能在唯一替代已存在、等价验证完成且流量/操作入口已经切换后退役；不能先删除旧工具再设计替代，也不能长期保留两个声称权威的发布入口。
