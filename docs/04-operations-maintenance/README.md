# 运行维护

## 分类目的与边界

运行维护在真实环境中观察产品和系统结果、控制高影响动作与事故，并把反馈、质量、成本、支持和维护事实转化为下一次明确决定。它不继续堆叠未筛选需求，也不代替上游重新定义价值、产品行为或工程方案。

## 根本原则

- **CATEGORY-OPERATIONS-001**：运行维护在合同 SLA、付费关键流程或高损失场景出现时，必须由人确认更高保障目标；评估则从真实信号中选择一个最高影响下一步，不维护无限待办。

## 包含的项目

- [运行](10-operation.md)：维持可持续保障，观察真实结果，并安全处置高影响动作、故障和恢复。
- [评估](11-evaluation.md)：汇总真实信号，形成一个决定和最高影响下一步，并维护必要知识与债务边界。

## 项目之间的关系

运行持续产生可观察事实，并在授权、影响范围和恢复边界内处置当前问题。评估消费这些事实，但不自动把每个信号变成需求；它选择继续、改进、回退、停止或维护，并把工作送回拥有相应决定的项目。评估确认需要长期保留的运行知识后，再形成维护记录。

## 进入条件

发布使能力进入真实环境、客户范围或持续服务后进入运行；出现告警、事故、高影响后台动作、凭据、安全、恢复或可用性问题时进入相应运行规则。反馈、指标、质量回归、事故结论、支持事实或维护信号足以影响下一步时进入评估。

## 结束或循环条件

当前运行事件在影响受控、状态可观察且恢复或交接明确后结束。评估在记录一个决定和一个最高影响下一步后结束：健康则继续观察，需要改变则只回到一个权威项目，需要长期沉淀则保留能支持未来判断或恢复的维护事实。

## 与其他分类的接口

从工程交付接收实际发布范围、观测和恢复边界；运行事实证明发布假设不成立时，可触发停止、回退或修复。评估发现价值或优先级变化时回到选题，证据不足回到调研，行为或体验变化回到产品设计，技术、实现、验证或发布缺口回到工程交付，从而闭合持续演进循环。
